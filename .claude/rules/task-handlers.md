# Background tasks gotchas

Reference: `docs/architecture.md` § Background Task Queue.

- `TaskRunner` poller thread starts inside `Telegram::Bot::Client.run` block, reuses `bot.api` — no second bot instance. Its forever-loop calls the testable `poll_cycle` boundary; that method catches dispatch/DB faults and reports them globally before the loop sleeps and continues.
- Background tasks are generic: `TaskRunner.register('type', HandlerClass)` + `BackgroundTask.create!(task_type: 'type', ...)` — add new task types via handler files in `lib/task_handlers/`
- `бот задачи` shows last 10 background tasks for the current chat. Agent turns use narrower `task_status`: strict positive Integer ID, or at most five newest user-facing image/Suno tasks ordered by creation/id. The no-ID path excludes `agent_event`, knowledge, cron, and housekeeping rows. Foreign IDs look absent; invalid explicit input errors rather than widening. Select compact lifecycle columns only—never params/results/`params_hash`, provider identifiers, URLs, prompts, or inline base64. Batch user text stays terse enough for the 2KB Runner cap; per-task truth lives in `items`, while the outer batch remains deferred/unknown unless every item is completed/delivered.
- **Migration 026 lifecycle schema** — `lifecycle_phase`, `delivery_status`, `retry_count`, and nullable indexed `parent_task_id` are canonical. Migration backfill is conservative and adds chat/time/type/phase plus message-correlation indexes. A historical correlated row proves delivery only for single-output image/WAV tasks, never multi-output song/cover/separation; uncertain completion stays unknown. Since this is a migration deploy, run `make backup` first. New handlers write lifecycle transitions explicitly through `BackgroundTask` helpers (or equivalent atomic updates); readers never reverse-engineer params JSON.
- **Counters and delivery semantics** — attempts are processing cycles; at runtime only `mark_retrying!` increments retry count (migration backfill seeds legacy rows once), including bounded cross-cycle delivery/persistence retries and explicit resubmits. While a bounded retry is still live, phase stays `retrying` and the whole task's delivery is `pending` (even if an earlier separation batch or song audio already arrived); `failed` delivery is terminal evidence only after exhaustion. Image and Suno tasks reach completed/delivered only after strict Telegram acknowledgement plus persisted message row(s). Receipt-backed persistence exhaustion is failed/delivered because Telegram accepted the media; pre-acceptance or partial separation exhaustion is failed/failed. Generic completion defaults unknown. Agent events write real `parent_task_id`, and song/separation delivery events update the parent's typed state. Missing/invalid/unavailable lookups return deferred/unknown evidence.
- **Never `sleep`/block in a handler** — TaskRunner has only 2 workers, and tool-path handlers run inside `bot.listen`'s single-threaded loop. Full war story: `.claude/rules/agent-runtime.md`.
- **Split production, external acceptance, and local persistence.** Cache a terminal paid/provider result before delivery and reset the poll-cycle attempt budget so pre-acceptance retries never regenerate and near-cap provider success still receives its bounded delivery window. After an external service accepts a send, persist a compact receipt before the local domain row and use later poll cycles only for bounded persistence reconciliation—never resend from a durable receipt. `SunoDelivery` applies this uniformly to song, cover-art, WAV, and separation; main-song lyrics use the same staged receipt protocol after audio, and multi-batch separation checkpoints and persists each accepted group before advancing. A task whose contract includes local tracking becomes `done` only after every required row exists. Distinguish delivery/partial failure from post-acceptance persistence failure in task state and agent events. Network retries return `:pending`; never loop, sleep, or resend inline inside the handler.
- **Exactly-once has an external crash gap.** Without a provider idempotency key, a process death between external acceptance and committing either the receipt or correlated local row is ambiguous. Document and test the durable no-resend boundary after a receipt, but do not claim strict end-to-end exactly-once delivery or speculate that a known receipt might be resent.
- **Validate acceptance evidence.** A truthy Telegram response is not enough: require its protocol identity—here, `message_id` must be an actual Ruby `Integer > 0`, not a numeric string—before caching a receipt or treating image delivery, Suno main/cover-art/WAV/separation media, direct failure notification, or Google media as accepted. Media groups must contain exactly the expected number of valid acknowledgements. Zero/negative/truncated/malformed truthy responses are unconfirmed failures. A valid receipt may truthfully set delivery delivered while phase is still `persisting_delivery`; completed/delivered additionally requires the centralized `Message.persist_bot_reply` path to succeed. Sanitize external exception strings and provider payloads through `Agent::ErrorReporter` before logs, raised retries, terminal task state, or model-facing events; never log raw signed result URLs.
- **Agent-event routing metadata is atomic.** Pass `user_notified` and `forum_thread_id` into `Agent::ErrorReporter.emit`; they belong in the `agent_event` params at creation time, not in a follow-up update that can race the worker or stale `params_hash`. When `user_notified: true`, `AgentEventHandler` marks the event done and returns before context/knowledge lookup or model/tool execution. Non-notified forum events scope context retrieval and response delivery to their stored `forum_thread_id`.
- **Post-success events are best-effort.** Informational event emission after a parent has already committed terminal success (for example `image_succeeded_after_retries`) must be rescued locally and may be dropped; it must never re-raise into TaskRunner, retry the parent, or overwrite the successful state.
- **Exceptions raised out of a handler are classified by message regex** (`TaskRunner::TRANSIENT_ERROR_RE` `\s5\d{2}[\s{]` → retried without spending an attempt; `PERMANENT_ERROR_RE` `\s4\d{2}[\s{]` → task failed immediately). Every terminal path is then passed to `Agent::ErrorReporter`: it keeps an existing tailored event for that parent task or creates a sanitized `runtime_error` event, so the failure reaches the agent instead of ending at the raw chat notice. A handler that wants a task-specific event/prompt should still fail and emit it itself (all Suno handlers do). A stray `" 4xx "` in a message makes it permanent — see `SunoClient#submit_error` for deliberate code rendering.
- `Agent::ErrorReporter` is the only generic failure bridge. Do not add new ad-hoc “print error to chat only” terminal paths. Generic task errors are deduplicated by `parent_task_id`; parentless errors coalesce by sanitized fingerprint for 5 minutes and use the 10/hour/chat cap; `agent_event` task failures are excluded to prevent recursive loops. Poller errors have no task chat, so `report_global` routes them to configured super-admin private chat IDs.
- **`params_hash`/`result_hash` are memoized and `reload` doesn't clear them** — in tests, assert persisted params via `BackgroundTask.find(id)`, not `task.reload.params_hash` (the latter reads the handler's in-memory mutation and passes even if the write was lost).
