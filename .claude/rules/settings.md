# Settings / rate limits gotchas

Reference: `docs/architecture.md` § Settings / § Configuration.

- `Settings` add-new-group note: top-level groups must be added to `REQUIRED_KEYS` in `lib/settings.rb` for the deep-merge validator to accept them. Settings file roles: `config/settings.common.yml` — non-secret defaults (prompts, models, URLs), committed; `config/settings.yml` — secrets & overrides, gitignored, deep-merged on top. Optional groups (e.g. `digests`) are deliberately NOT in `REQUIRED_KEYS` — see `.claude/rules/agent-games.md`. Nested keys under an existing group don't need a `REQUIRED_KEYS` entry either — e.g. `image_gen.models` / `image_gen.default_model` (the agent-selectable image-model catalog); adding or switching an image model is a config-only edit.
- **`telegram.rich_messages`** (default `true`, committed in `settings.common.yml`) — master switch for Bot API 10.1 Rich Messages in `MessageSender#send`. Non-secret default lives in common.yml and deep-merges under the `telegram.token` from the gitignored `settings.yml` (the `deep_merge` is recursive, so both coexist). Kill switch: set `telegram.rich_messages: false` in **prod** `settings.yml` — but note Settings load **once at boot**, so it only takes effect after a **restart**. No `REQUIRED_KEYS` change needed (nested key under the already-required `telegram` group). See `.claude/rules/messages-context.md` for the send-path behavior.
- **Per-role rate limits** — `Settings.auth['rate_limits']['admin'][service]` overrides the regular bucket when `RateLimiter.exceeded?(..., role: 'admin')` is called with `role: 'admin'`. Tools pass `ctx[:user]&.role`. Counters stay per-chat-shared (no per-user counter). For **admins**, the effective limit is `RateLimiter.more_permissive(chat.rate_limits.<svc>, auth.rate_limits.admin.<svc>)` — the higher max-per-minute of the two — so a super-admin *raising* their own cap via the /admin menu applies (the 2026-07-24 fix; before, the admin default silently overrode any menu edit — a trap), but a *restrictive* per-chat/config-seeded value can't drop an admin below the admin override. **Non-admins** use `chat.rate_limits.<svc>` directly. NOTE: menu edits AND config seeds both live in `chat.rate_limits` (`Chat.sync_from_config!` writes the same column), so they're indistinguishable in code — that's why admins take the more-permissive of the two rather than "menu edit always wins". Full order — non-admin: `chat.rate_limits.<svc>` → `auth.rate_limits.<svc>` → hard-coded `{max:1,window:20}`; admin: `more_permissive(per-chat, admin-override)` → default → hard-coded.

- **`knowledge.subject_aliases` is personal data.** It maps Telegram uids to the given names, diminutives and nicknames people are called by in chat, and it is the first settings key holding data about individuals. This repo is **public**, so that map is a deanonymization table for a private community — it lives only in the gitignored `config/settings.yml`, is never committed, and per CLAUDE.md is never scp'd (edit the prod copy in place over ssh). `rake knowledge:backfill_subjects` reads it from Settings and no-ops with instructions when it is absent.
