# Knowledge base / embeddings gotchas

Reference: `docs/architecture.md` § KnowledgeBase / § EmbeddingCache / § EmbeddingService.

## Storage

- **NEVER make a network call inside an ActiveRecord transaction.** Transactions on this stack are **DEFERRED** — the sqlite3 gem's default mode, and AR 7.2 passes none (`BEGIN IMMEDIATE` by default is a Rails 8 change). SQLite takes the write lock at the transaction's *first write* and holds it until COMMIT. With `busy_timeout` 5000, every other writer — including the listen loop saving each incoming message — fails after 5 s. `extract_and_store` embedded each fact inside its batch transaction for 24 days, holding the lock across embeds 2..N of every batch: 48 `BusyException`s, 27 unsaved chat messages, `bot.listen` frozen up to 10 s each time. Embed first, then open the transaction; `KnowledgeBase.add` takes `embedding:` for exactly this. The code reviewer had flagged it and a scripted "fix" silently failed to apply — the guard tests now assert `open_transactions == baseline` during every embed (stricter than the lock: no network anywhere inside a transaction) **and** include a negative control proving the detector sees a real transaction.
- **DEFERRED-mode trap in WAL:** a transaction that has *already read* gets `SQLITE_BUSY` **at once**, without waiting out `busy_timeout`, if another connection holds the write lock **or** has committed since its snapshot — SQLite skips the busy handler for any transaction holding a read snapshot. Retrying the statement can't help; only restarting the transaction can. Start write transactions with the write (measured with sqlite3 2.9.3: read-then-write fails in 0 ms; write-first waits the full timeout). Both knowledge write transactions begin with an INSERT today.
- Embeddings live in `embedding_blob` — packed float32 via `Array#pack('f*')`, ~6 KB/row. The legacy `embedding` TEXT column (JSON, ~29 KB/row) is written only while `knowledge.dual_write_legacy` is on — **off by default since 2026-09** — and read only as a fallback for rows with no blob.
- **Never write packed bytes to `embedding`.** AR 7.2 + sqlite3 2.x raise `Encoding::UndefinedConversionError` binding an ASCII-8BIT string with high bytes to a `text` attribute. That is why migration 023 added a separate `binary` column instead of reusing the old one.
- `pack('f*')` is **native-endian** and must stay paired with `Numo::SFloat.from_binary`, which is also native. Restoring `bot.db` onto a big-endian host would misread; recovery is a re-run of `rake knowledge:pack_embeddings`.
- Dual-write was the rollback path for 023, and is now off: facts are blob-only, so reverting to code that predates 023 would make them unsearchable. `rake knowledge:unpack_embeddings` rebuilds the JSON from blobs if that is ever needed. `rake knowledge:drop_legacy_embeddings` (refuses while any row still has JSON but no blob) clears the old column; `VACUUM` reclaims the file space but needs the bot stopped.

## EmbeddingCache

- Invalidation is an **`after_commit` callback on `Knowledge`**, not discipline at each call site — a stale cache means silently wrong search results. `update_all` / `delete_all` / raw SQL bypass it. The offline backfill deliberately uses `update_all` (storage format changes, vector values don't).
- `after_commit` fires **only in the writing process**. `rake knowledge:compact` and `bin/console` mutate `knowledge` from a separate process, so a running bot keeps serving its already-built matrix until its next in-process write to that chat: merged facts stay invisible and result pages silently shorten. Deleted rows can't resurrect (`search` re-loads the top-K by id), but **restart the bot after any out-of-process knowledge mutation**. `rake knowledge:compact` prints a reminder.
- **`EmbeddingCache.fetch` must never block.** The per-chat build lock uses `try_lock`, never `synchronize`: `fetch` is reached from `bot.listen`'s single-threaded loop as well as the extraction `Thread`, TaskRunner and CronScheduler, and a cold build on the legacy JSON path takes ~1.7 s. A thread that loses the race builds its own copy instead of waiting.
- Any test that writes `Knowledge` rows must call `EmbeddingCache.reset_for_test!` in `setup`/`teardown` — the per-test transaction rollback otherwise leaves a cache built from rolled-back rows.
- A rebuild may read the legacy JSON column **only for rows with no blob** (a separate restricted query, then re-sorted by id — `search` tie-breaks on position). Plucking it for every row made Ruby allocate ~171 MB of JSON strings per rebuild; p50 765 ms in prod. `test_rebuild_reads_legacy_json_only_for_rows_without_a_blob` pins this at the SQL level. **This only partly helps while the JSON is still on disk:** `embedding_blob` was added *after* `embedding`, so SQLite still reads through each row's JSON bytes to reach the blob (measured 80 ms → 45 ms on a synthetic table, and → 16 ms once the JSON is nulled). The full win needs `rake knowledge:drop_legacy_embeddings`.
- Rows whose embedding length differs from the chat's modal length are dropped and warned about. `Numo`'s `cast` silently zero-pads ragged arrays, so a change of embeddings model would otherwise corrupt every score with no error.
- Norms are clamped (`maximum(norms, 1e-12)`): a stored zero-norm vector used to yield `NaN`, and `NaN` makes `sort_by` raise `ArgumentError` deep inside `search`.

## Dedup

- **One pipeline, one deleting actor.** `Cluster` proposes candidates, `Review` judges and applies. Nothing else deletes facts. `compact!`/`merge_cluster` and the `knowledge_compact` task type are gone; `KnowledgeBase.review!` replaces them.
- **Same-batch duplicates are collapsed at extraction, before saving** (`BatchDedup`). The extractor often states one conversation twice in a 3–7 fact batch, and those siblings were the main ongoing source of duplicates — the persisted sweep was the wrong tool (min-age wait, tombstones, budget). Batch pairs ≥ `batch_dedup_threshold` (0.50) go to the same judge; any failure keeps the originals. Batch prompt ids are 1-based **positions**, not DB ids — nothing is saved yet.
- **There is no threshold gate against the existing base.** The old `similar_exists?` rejected only above 0.92 cosine; measured over all 18.8M pairs of the prod main chat the maximum similarity between any two facts is **0.6994**, so it never fired once. Deleted. Don't reintroduce a threshold gate without measuring the corpus first.
- **Two similarity spaces, never mixed in one clustering pass.** G1 is raw cosine at 0.66; G2 is the per-person centroid-removed residual at 0.42. The pairs G2 exists to find sit at *raw* cosine 0.58–0.66, so any raw-space admission test silently discards them — which looks like "fewer clusters", not like an error. Cluster each space separately and union the resulting **clusters**, never the pairs.
- **G2 emits first and claims its facts**; G1 runs over the remainder. That is what guarantees a fact never lands in two clusters, so no merge operates on a row another merge already soft-deleted.
- `subject_min_residual` ships at 0.0 (disabled) because the measured residual-norm distribution on prod is min 0.64 / p10 0.73 / median 0.81 — nothing sits near a centroid. That is a measurement, not an oversight; `rake knowledge:cluster_preview` prints the distribution to re-check it.
- **G2 is the productive generator, and it is deliberately loose.** Measured against the real judge: G2 supplied 9.7% of candidates but **64% of the merges** (23% hit rate vs G1's 4.4%). Its threshold is 0.42 even though the raw clusters there look bad to a human — the judge is the precision filter, and judging clusters that exist only at 0.42 gave the same ~20% hit rate with correct merges, including near-verbatim duplicates 0.55 could not reach.
- **Do not tune a candidate threshold by eyeballing raw clusters.** That is how G2 first got set to 0.55, which cut candidates from 414 to 30 and threw away ~3x the yield for no quality gain. Judge quality is measured on the judge's OUTPUT: run `rake knowledge:review DRY_RUN=1` and read the merges it proposes.
- Nothing exists above ~0.65 in the residual space, so there is no headroom above the current setting. Re-run `rake knowledge:cluster_preview` (no LLM, no writes) to inspect candidate shape before changing anything.
- **The judge must be allowed to refuse.** Candidate precision is ~67–80%, so refusing is the normal case. The old `MERGE_PROMPT` asserted the cluster *was* duplicated and only asked for merged text — at this precision that reliably fuses distinct facts. The "same person, different fact" trap is the one to guard against.
- Never trust the verdict. Shared by the sweep and `BatchDedup` (`Review.request_verdict` + `Review.valid_merges`): treat a non-object verdict as unparseable (a top-level JSON array used to raise out of the run), drop ids outside the chunk, drop merges of fewer than 2 ids, first-wins on overlapping groups. Owned by each caller, NOT by `valid_merges`: merge winning over delete for the same id, and — in the sweep's `apply` — log-but-don't-apply anything over the budget.
- **A merge larger than the whole daily cap can never fit — rule it out, don't wait for it.** Treating it like "no budget left today" (`cap_reached`) left its cluster unstamped at the head of the queue, ending every later run after one paid call: a permanent stall (`max_cluster` 8 vs `max_delete_per_day` 5). It is logged, counted as `oversized`, and the cluster counts as resolved. Only a proposal that *could* fit on a later day leaves its cluster unstamped. **The cap depends on the chat's size** — the lower of `max_delete_per_day` and `max_delete_pct` of live facts — so at the defaults (5, 2%) the percentage decides below 250 facts: 4 at cron's 200-fact floor, and 1 on a 60-fact chat reviewed via `бот ревизия знаний`, where every merge is oversized and stamped for `ttl_days`.
- **Never tombstone sources behind a merged fact without an embedding.** `EmbeddingService.embed` returns nil on any failure; a vectorless merged fact is invisible to search and review while its sources die in the same transaction. `apply_merge` writes nothing when the embed fails, and the cluster is retried. `BatchDedup` keeps the originals in the same case.
- `BatchDedup` honours `delete` with reason `duplicate` (the shared prompt calls a verbatim restatement a delete, not a merge). Other delete reasons are logged and ignored: a fresh fact is not dropped for being "trivial". **The survivor must be known, never inferred from "someone else in the group survives":** batch groups chain similar pairs, so in `[A, B, C]` with only A and C duplicates, B surviving says nothing about their content — dropping both A and C (each "a duplicate of the other") would lose it permanently, since nothing was saved yet. With `of`, that exact fact must survive (directly or folded into a merge), no fallback; without `of`, only a two-member group is unambiguous. The dropped fact's subjects move to that survivor. The judge prompt asks for `of`.
- `review!` records its log row in an `ensure`: merges applied before a mid-run exception must still be charged to the 24h budget, which is computed from that log. It tracks success with an explicit flag, not `$!` — `$!` is also set while a *caller* is handling an exception. A failed run leaves a log row, so `maybe_trigger_review`'s cooldown applies before re-enqueueing.
- **Eligibility is decided BEFORE the judge, never by discarding its verdict.** Facts younger than `min_age_days`, judged within `ttl_days`, or `manual` are pre-claimed (`unavailable_for_review`) so they never enter a cluster — and are not stamped. The first version dropped a young fact's approved merge and then stamped it anyway: every new fact got one look while too young to act on, then a 30-day lockout. **All 14 merges the judge proposed in the 24 days after launch died that way.** A post-verdict age check in `apply` remains only as defence in depth.
- G2's per-bucket `seed_and_absorb` must be seeded with the unavailable set. Proposing with an empty claim set and filtering at acceptance throws away a whole `[a, b, c]` proposal when only `c` is unavailable, losing a good `[a, b]`.
- **Deletion is soft.** All read paths go through `scope :live`; the enumerated call sites include `EmbeddingCache#build` and the subject-bucket queries — a tombstone left in a bucket pollutes its centroid and comes back as a candidate. `бот верни <id>` restores, and refuses on a `merged` source unless confirmed.
- **The daily deletion budget counts merge-sourced deletions** (a 3-fact merge spends 3) and is shared across every run that day, summed from `knowledge_compact_log.removed` — which is the TOTAL soft-deletes for a run, with `deleted` a breakdown of it. Summing both charges a direct deletion twice. Merging is by far the bigger deletion vector; a cap governing only the `delete` array understates the blast radius by an order of magnitude.
- `knowledge_subjects` has the schema's **first FK**, and sqlite runs `PRAGMA foreign_keys = ON` — `on_delete: :cascade` plus `dependent: :delete_all` are both required or every `Knowledge#destroy` raises.
- A single verdict can propose **overlapping merge groups** ([1,2] and [2,3]); apply only the first, or the shared fact is deleted twice and the second merged fact quotes a source already merged away. Treat every verdict element as untrusted shape too — `{"delete":[3]}` is valid JSON and must not raise.
- Build prompts with `gsub('{X}') { value }`, never `gsub('{X}', value)`: a string replacement expands `\\1`, `\\&` and `\\\\` occurring in fact content or JSON escapes, silently mangling what the model sees.
- **Facts judged within `review.ttl_days` are skipped** by candidate generation, which is what makes runs resumable and stops a just-merged fact being re-merged. A dry run must never stamp `reviewed_at`.
- **Stamp only what the judge actually ruled on** (`Review.run`'s `judged_ids`). Not clusters the run never reached (`max_chunks`, budget), not unparseable answers, not a cluster whose verdict a cap cut off. Stamping every candidate — the first version — marked 1,250 facts on day one against ~650 judged and silently locked the rest out for 30 days. The symptom of getting this wrong is not an error; it is a sweep that runs daily, pays for LLM calls, and merges nothing.
- A merged fact's subjects are the **union of its sources'**, and it is stamped `reviewed_at` at creation — otherwise it drops out of its buckets, shifts their centroids, and jumps to the head of the next sweep to be re-merged.
- **`knowledge.subject_aliases` is personal data and lives only in the gitignored `config/settings.yml`.** This repo is public; a uid→given-name/nickname map for a private community is a deanonymization table. Never match on a bare `users.first_name` — it is not unique, and collapsing two people into one bucket produces confident, wrong clusters.
- `KnowledgeBase.compact_logger` falls back `COMPACT_LOGGER → LOGGER → IO::NULL`. `COMPACT_LOGGER` is assigned only in `lib/bot.rb`, so the review path used to raise `NameError` from rake tasks and `bin/console`.
- `бот ревизия знаний` (admin only) **enqueues** a background task. It must never run the sweep inline — one LLM call per cluster would freeze the whole bot.
