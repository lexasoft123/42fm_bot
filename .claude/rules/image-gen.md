# Image generation gotchas

Trap knowledge for the image-gen adapter layer (FLUX / Atlas Cloud / CloseRouter Nano Banana Pro). Reference: `docs/architecture.md` § Image generation.

| Task | File |
|------|------|
| Image generation (FLUX / Atlas Cloud / CloseRouter Nano Banana Pro) | `lib/image_gen/*.rb` + `lib/model_provider_client.rb` + `lib/task_handlers/image_gen_handler.rb` + `lib/agent/tools/image_gen.rb` (agent-only, no direct command) |
| Auto-awards (🏆 images) | `lib/agent/tools/award.rb` (`make_award`) → `image_generate` task with `award: true`; caption via `ImageGenTaskHandler#caption_for` (shared by sync + async delivery) |

- Image generation is agent-only — `generate_image` creates an `image_generate` task and returns evidence keyed by `action: generate_image`, positive `task_id`, and `task_type: image_generate`. Preserve that identity; newer `task_status` evidence supersedes the queued acknowledgement. Image lifecycle writes are explicit: processing, delivering/pending, persisting_delivery/delivered, then completed/delivered; delivery/persistence retry paths increment `retry_count`. This terminal invariant is why a done image may claim delivered—never infer that from coarse status for other task types. Prompt enrichment remains the dedicated bounded DeepSeek/comedy-first pass; any provider failure, exception, refusal, or blank output falls back immediately to the raw request without consuming image retries or blocking backend submission.
- **Generation success is not Telegram acceptance, and acceptance is not local persistence.** Cache every terminal sync/async provider result in `task.params['delivery_result']` while the task remains pending, and check that cache before `external_id` on every handler call. Before acceptance, transport/TLS failures and Telegram 429/5xx return `:pending`; other 4xx responses (including `IMAGE_PROCESS_FAILED`) are permanent. A truthy send response counts as accepted only when its serialized receipt contains `message_id` as a Ruby `Integer > 0`; numeric strings, zero/negative values, and malformed responses are unconfirmed delivery failures, not receipts. Never `sleep` or retry inline. Once Telegram accepts, cache a compact `delivery_receipt` **and delete the entire provider `delivery_result` in the same params write**; receipt-driven persistence/events/re-entry need no provider URL or payload, and later persistence retries must not restore it. Reconcile `Message.persist_bot_reply` for at most `MAX_PERSISTENCE_FAILURES` cycles without resending. Also reconcile an existing bot row by `bg_task_external_id` (`external_id`, or `image-task:<id>` for sync tasks) before any send. Mark `done` only when the accepted message is locally persisted/reconciled. Exhausted/nonretryable pre-acceptance failures emit `image_delivery_failed`; exhausted post-acceptance DB reconciliation emits `image_persistence_failed`. Neither event may trigger automatic regeneration.
- **No strict external exactly-once guarantee.** The durable receipt prevents resends after it is stored, but a crash after Telegram accepts the photo and before either receipt or correlated `Message` row commits is inherently ambiguous because `sendPhoto` has no idempotency key. Do not document this as exactly-once delivery.
- **Failure notices belong to the agent loop** — terminal image failures enqueue an `agent_event` with `user_notified: false`, a sanitized summary containing the parent task ID, bounded provider reason when available, and the originating `forum_thread_id`. `AgentEventHandler` loads thread-scoped context and must produce the user-facing explanation in that same topic. It caches the reply before sending, requires Telegram's `message_id` to be an `Integer > 0`, stores the acknowledgement before persistence, and retries persistence without resending or rerunning the agent. If the event is rate-limited or its insert fails, enqueue a dedicated `failure_notice` task instead of performing a best-effort inline send; `FailureNoticeHandler` applies the same receipt-first persistence contract and bounded TaskRunner retry, and `Agent::ErrorReporter` treats it as the specialized parent event. The event handler uses a task-ID-bearing fallback only when its queued agent turn raises or returns blank/`(skip)`. Other feature handlers that genuinely notified the user may still set `user_notified: true`; those events are consumed before context/LLM/tool work to prevent duplicates. Pass `user_notified` and `forum_thread_id` into `Agent::ErrorReporter.emit` on initial insert; never mutate event params afterward.
- **Sanitize the whole image lifecycle** — pass every provider/Telegram-derived string through `Agent::ErrorReporter.sanitize` before logs, raised retry exceptions, persisted failure state, task/event details, or model-visible output. This includes adapter resolution, submission, polling results/errors, delivery, downloads, tempfile cleanup, and terminal missing-URL diagnostics. Sanitization starts at the source: `FluxAdapter` and `AtlasAdapter` sanitize ids/statuses/errors/bodies in their own log/raise paths, while `ModelProviderClient` sanitizes tags, paths, transport errors, and redacted/truncated non-2xx bodies. Never log a raw signed completion URL: success logs use `URL redacted`. The unsanitized provider result may exist only in a pending pre-acceptance task while it is still required to deliver the image; receipt caching removes it rather than retaining a redacted placeholder, while terminal pre-acceptance failures still recursively sanitize any cached result.
- **Per-request model selection** — `generate_image` has a `model` enum; the agent picks a catalog key. `ImageGen::Catalog` (`lib/image_gen/catalog.rb`, backed by config `image_gen.models`) maps key→`{provider, t2i, edit, desc}`. The handler picks the adapter **by the entry's provider** (not just `current_adapter`), validates it against `ImageGen::ADAPTERS` (unknown provider → re-resolve to `default_model` so adapter+model id stay coherent), snapshots both `provider` and `model` into params, and threads the provider-specific id into `adapter.submit(model:)` (nil ⇒ adapter's configured default). Missing/invalid key → `image_gen.default_model`. `edit: false` entry → edit falls back to the adapter's `image_edit_model`.
  - **Lazy enum (load-order trap):** Settings is NOT loaded when tools are required (`boot.rb` requires `message_responder` → tools before `app_configurator` runs `Settings.load!`). So the `model` enum/description can't be in the static `parameters:` hash — the tool uses `enum_source`/`desc_suffix_source` **lambdas** resolved in `ToolRegistry.definitions_for` (per-turn, at runtime). `ToolRegistry.build_properties` strips those internal keys and `optional:` from the emitted JSON schema; `required` now excludes `optional: true` params (was a latent "all params required" bug).
  - **model_name interpolation:** the shared prompt templates use `%{model_name}`. The handler passes `model_name:` on **every** interpolation path (incl. `make_award` tasks with no `model` key → `'AI image generator'`) because Ruby `String#%` raises `KeyError` on a missing referenced key.
- **Atlas edit image field is PER-MODEL family** — the killer trap. `AtlasAdapter#submit` builds the edit body differently by model id: **Wan** (`alibaba/wan-2.7/image-edit`) reads singular **`image:`**; the **nano-banana + Seedream + GPT Image families** (`google/nano-banana-*/edit`, `bytedance/seedream-v5.0-pro/edit`, `openai/gpt-image-2.5-sunburst/edit`) read plural **`images:` array**; **Qwen Image 3.0** (`qwen-image-3.0-*/edit`) reads **`reference_image_urls:`** and accepts at most 3 items. Send the wrong field and a model may **silently ignore the source and regenerate from scratch** — the task still succeeds, so it never surfaces as a failure. All accept base64 data URIs directly — no `uploadMedia`/public-URL step (nano-banana confirmed live 2026-06-24; Qwen and GPT Image verified in Atlas docs 2026-09-22). The adapter trims Qwen inputs to 3 and logs when the tool-wide cap supplied more. CloseRouter (`nano-banana-pro`) always uses `images:`; Flux uses singular `input_image` (its own API field).
- **Atlas T2I sizing is PER-MODEL too** — Wan/nano-banana take `width:` + `height:` **integers**; **Seedream and Qwen Image 3.0** take **`size: "WIDTH*HEIGHT"`**; **GPT Image 2.5 Sunburst** takes **`size: "WIDTHxHEIGHT"`** (letter x). Seedream size must stay within 1024×1024…2048×2048 total px; Qwen 3.0 supports 512×512…2048×2048 for T2I. Seedream is flagged `multi_image: true` (combines up to 10 refs, above the `MAX_EDIT_IMAGES` cap of 6); Qwen is also flagged multi-image but the adapter enforces its 3-ref limit. Atlas documents up to 16 references for Sunburst, but the shared tool cap remains 6.
- **Multi-image edit / combine + chat-history sourcing** — `generate_image` takes `source_message_ids` (array of Telegram `message_id`s of earlier `photo: true` messages) on top of the current/replied photo. Sources resolve in **two places by design**: the inline current/reply image is base64 in `ctx[:image]` at tool time; **history images are downloaded in `ImageGenTaskHandler#resolve_input_images` (runs in TaskRunner), NEVER in the tool** (the tool runs in the bot's single-threaded listen loop — no blocking network I/O; see `agent-runtime.md`). Reuses the `view_image` resolution (`Message…pick(:attachment_photo_file_id)` → `TelegramFile.download_image`). Order = inline first, then history. Stale/old message_ids (no stored file_id) are **skipped + warned**; if an edit was intended but **zero** images resolve, the task **fails with a user-facing notice** instead of silently doing text-to-image (the exact silent-degradation this exists to kill). Cap: `ImageGen::MAX_EDIT_IMAGES` (6) total. Adapters take `input_images:` (array of `{data:, media_type:}`); single-image adapters (Atlas-Wan, Flux) use the **first** + log if more.
- **Multi-image capability + auto-switch** — only catalog entries flagged `multi_image: true` (nano-banana, Seedream, Qwen 3, GPT Image 2.5 Sunburst) actually combine multiple inputs (`ImageGen::Catalog.multi_image?`); model-specific adapter limits still apply (Qwen: 3; shared tool cap: 6). When the agent picks an **incapable** model (Wan/Flux) for a `>1`-image request, the `generate_image` tool **auto-switches to `default_model`** so the user gets the combine. Adding the flag to a model is a config-only edit.
- **Image-gen adapter dispatch** — `Settings.image_gen['provider']` selects the backend for legacy/no-model tasks (`'flux'` | `'atlas'` | `'closerouter'`). `ImageGen.current_adapter` is read on submit for those; catalog-keyed tasks call `adapter_for(entry_provider)`. The chosen `adapter.name` is snapshotted into `task.params['provider']`; `ImageGen.adapter_for(provider)` is read on poll, so a config flip (e.g. `docker compose up -d --build` mid-flight) doesn't reroute polling to a different prediction id space — old tasks continue against the original backend, new tasks go to the new one.
- **Synchronous image adapters** — `Adapter#synchronous?` predicate (defaults `false`). When `true`, `#submit` returns a terminal result Hash (`{url:, completed:true}`) instead of an external_id String; `ImageGenTaskHandler` short-circuits polling in `deliver_sync_result`, caches the result, and enters the shared delivery path. It still cannot mark the task done until send + persistence succeed. `#poll_once` raises `NotImplementedError` if reached. Only `CloseRouterImgAdapter` is sync today (CloseRouter's `/v1/images/generations` returns the result in the same response). Flux + Atlas stay async.
- **Poll-error handling (Atlas 500s) — the "stuck pending" trap.** `AtlasAdapter#poll_once` returns **`:poll_error`** (NOT `:pending`) on any non-200 status poll (incl. the `[nil,nil]` SSL/timeout that `ModelProviderClient#get` swallows). Atlas's status endpoint returns HTTP **500 persistently for some FAILED predictions** — Atlas web shows them failed while a naive poller would sit `:pending` until the 60-attempt (~15min) timeout, then fail with a misleading "таймаут" message. `ImageGenTaskHandler#poll_and_deliver` tolerates up to `MAX_POLL_ERRORS` (5 ≈ 75s) **CONSECUTIVE** poll errors (counter in `task.params['poll_errors']`, **reset on any healthy 200 poll** via `reset_poll_errors`) then `mark_failed_and_notify(..., 'poll_unavailable')` → proper "Не удалось сгенерировать картинку" + agent event. So single transient blips are absorbed; a persistent outage fails fast and notifies. (Diagnosed 2026-07-24: a live prediction logged 30 consecutive `code=500` → `:pending`; 320 such 500s across the log.)
- **`ModelProviderClient`** (`lib/model_provider_client.rb`) — generic Bearer+JSON HTTP client (formerly `AtlasClient`). `POST` raises on non-2xx; `GET` returns `[code, body]` and swallows transient SSL/timeout (returns `[nil, nil]`). Constructor takes a config dict + `tag:` for greppable logs (`'AtlasImg'` / `'CloseRouterImg'` / future `'CloseRouterVideo'`). Reusable by any future Bearer-token, JSON-body model provider.
- **Image-gen settings** in `config/settings.common.yml` under `image_gen:` block (`provider` + `providers.atlas` + `providers.flux` + `providers.closerouter`); api_keys in `config/settings.yml`. The catalog and Atlas legacy defaults are all `qwen-image-3-pro` / `qwen-image-3.0-pro/*`, so omitted-model and legacy tasks stay coherent. Prompt-composer model/budget lives separately at `chat_gpt.settings.image_prompt`; never route enrichment back through `agent`/`agent_vision`. `FluxAdapter` has a one-release back-compat shim that reads top-level `Settings.flux` if `image_gen.providers.flux` is missing — removed once prod settings.yml is migrated. CloseRouter's `providers.closerouter` has `text_to_image_model: 'google/nano-banana-pro'` + `image_edit_model: 'google/nano-banana-pro-edit'` (separate model ids — edit is not a parameter on the base model).
- FLUX API settings: top-level `flux:` block in `settings.yml`/`settings.common.yml` is the legacy location read by FluxAdapter's back-compat shim. New canonical location is `image_gen.providers.flux.{api_url,api_key,model}`.
- **Award captions** — `ImageGenTaskHandler#caption_for` is the single caption builder for BOTH delivery paths (sync CloseRouter + async Flux/Atlas); `award: true` params → `🏆` prefix.
- **Awards preserve topics and provenance** — `make_award` snapshots `ctx[:forum_thread_id]` into the `image_generate` task exactly like `generate_image` and returns the same trusted `generate_image`/`image_generate` queued action identity with the real task ID. This lets later `task_status` evidence supersede the award acknowledgement instead of leaving two unrelated provenance records. Do not drop either property when adding alternate image-task enqueuers.
- **Recovery events cannot change success** — after a retrying generation is durably delivered/persisted and its parent marked done, `image_succeeded_after_retries` emission is best-effort. Rescue and sanitize any event-creation error; never let this secondary event re-raise into TaskRunner or alter the terminal parent state.
