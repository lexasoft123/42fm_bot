# Suno gotchas

Trap knowledge for Suno song generation, add-vocals, cover-audio, cover-art, and WAV export. Reference: `docs/architecture.md` § SunoClient (+ its subsections).

| Task | File |
|------|------|
| Suno song generation | `lib/suno_client.rb` + `lib/task_handlers/suno_handler.rb` + `lib/agent/tools/suno.rb` (agent-only, no direct command) |
| Suno add-vocals (sing along user audio) | `lib/agent/tools/add_vocals.rb` → `suno_add_vocals` task (handled by `SunoTaskHandler`); 1 clip output |
| Suno upload-cover (musical cover) | `lib/agent/tools/cover_audio.rb` → `suno_cover_audio` task (handled by `SunoTaskHandler`); 2 clip output |
| Suno cover-art (album images) | `lib/agent/tools/cover_art.rb` → `suno_cover_art` task → `lib/task_handlers/suno_cover_art_handler.rb`; 2 PNG output via sendMediaGroup |
| Suno WAV-export (mp3 → wav) | `lib/agent/tools/convert_to_wav.rb` → `suno_wav_convert` task → `lib/task_handlers/suno_wav_convert_handler.rb`; sent as Telegram audio so user can play AND download |
| Suno vocal/stem separation (минус, стемы) | `lib/agent/tools/separate_vocals.rb` → `suno_separate_vocals` task → `lib/task_handlers/suno_separate_vocals_handler.rb`; stems sent as audio media groups (≤10 each) |
| DM "send the audio next" follow-up | `lib/pending_audio_request.rb` (registry) + `MessageResponder#run_pending_audio_followup` (replay) — offered by `cover_audio` / `add_vocals` / `separate_vocals` when no source |
| Which audio a request refers to | `lib/audio_attachment.rb` — `AudioAttachment.resolve` (current msg → reply target → ≤30-min lookback), used by `GptChat#attached_audio` |
| Shared media download | `lib/media_download.rb` — `MediaDownload` module included by the Suno handlers (download URL → Tempfile) |

- Suno song generation is agent-only — the `compose_song` agent tool creates a `suno_generate` background task (no direct `бот спой` command). Suno returns 2 clip variants; delivery requires downloading **all** variants, naming them `Performer_-_Song_Name.mp3`, and sending one complete media group. Never silently send the subset that happened to download.
- Suno model: `suno.model` default `V6_WILD`, with `suno.models` (`V6_WILD`, `V6`, `V5_5`) selectable per request (see the model bullet below); lyrics + tags are produced **handler-side** in a SINGLE combined Claude Sonnet 5 call with thinking disabled (`compose_lyrics_and_tags`, `purpose: 'suno_compose'`, returns `<lyrics>…</lyrics><tags>…</tags>` XML blocks) on the common path where the user hasn't supplied verbatim lyrics. When the user DOES supply verbatim lyrics, the handler skips composition and runs the tags-only call (`resolve_tags`, `purpose: 'suno_tags'`). The `compose_song` agent tool does NOT take a `tags` arg (only intent: `artist`/`genre`/`theme`/`title`). Always-enrich is structural, not heuristic. Artist names are **never** included in tags (Suno blocks them). `TAGS_PROMPT` orders tags *genre → mood → instruments → vocals → mix*; negatives flow through the structured `negative_tags` param on `compose_song`/`add_vocals`/`cover_audio` (shared description: `SUNO_NEGATIVE_TAGS_DESC` in `_suno_language_rule.rb`), never inlined into `tags`. Detail: `docs/architecture.md#tag-ordering-convention-tags_prompt` + `#lyric-craft-directives-lyrics_prompt` + `#combined-compose-call`.
- **Genre-language rule** for Suno-bound lyrics/topic content (compose_song, add_vocals, cover_audio): the language of the SUNG text follows the GENRE'S native language, not the user's request language. Russian-origin genres (частушка, шансон, бардовская, советский рок/панк/эстрада) → Russian; everything else (rock, metal, pop, surf rock, blues, jazz, hip-hop, country, electronic, etc.) → English by default, even if the user asked in Russian. Section markers (`[Verse]`, `[Chorus]`...) and parenthetical stage directions inside blocks are ALWAYS English regardless of genre — Suno's style vocabulary is English-trained. User can override explicitly ("сделай рэп НА РУССКОМ"). Canonical rule wording: `SUNO_LANGUAGE_RULE_RU` constant in `lib/agent/tools/_suno_language_rule.rb`, interpolated into all three Suno tool descriptions; duplicated word-for-word in `Settings.suno['lyrics_prompt']` (the YAML side has no Ruby interpolation). New Suno tool? Reuse the constant.
- **Suno add-vocals / cover-audio / cover-art** — three additional agent tools layered on Suno: `add_vocals` (sing AI vocals over user-provided audio, 1 clip), `cover_audio` (musical cover/re-style of user-provided audio, 2 clips), `cover_art` (2 album-art PNGs for an existing Suno song). Audio inputs come from Telegram attachments (`message.audio` / `message.voice` / `message.document` with `audio/*` MIME — `attached_audio` helper in `lib/commands/gpt_chat.rb`) OR from agent-supplied URLs. `attached_audio` → `AudioAttachment.resolve` priority chain: (1) current message (`source: :message`); (2) reply-target message (`:reply`); (3) most recent attachment within the last 20 rows **and last 30 minutes** of the chat (`:lookback`, DB lookback via `messages.attachment_file_id`; thread-filtered only when `chat.is_forum`). The lookback covers the "user uploaded an audio earlier, then asked for a cover in a fresh message without using Telegram-reply" case. **The time bound is the trap fix**: rows alone don't bound staleness — prod 2026-08-24 a quiet DM's 20-row window reached a 12-day-old upload and `cover_audio` covered the wrong song; 2026-09-04 a 7-hour-old group upload turned "бот спой движуха песню" into a DDT cover. `Runner#audio_hint` words `:lookback` audio as "НЕ прикреплено, N мин назад прислал X — используй только если запрос явно про него" and passes `tool_ctx[:audio_source]` so a tool can tell an attachment from an implied source (`separate_vocals` uses it; `cover_audio`/`add_vocals` still upload whatever resolved). Don't loosen the bound or present lookback audio as "attached". `ChatContext.serialize_msg` adds `audio: true` to context entries so the agent sees which past messages have an attachment. The Telegram file URL contains the bot token; sending it to Suno leaks the token to Suno's logs — pre-existing risk profile (the bot already exposes that URL to chat for voice messages); rotate via @BotFather if needed.
- **`cover_audio` lyrics-vs-topic split** — tool exposes two args: `lyrics` (verbatim → custom mode, ≤5000 chars) and `topic` (theme seed → auto mode, ≤500 chars). Reply to a prior bot song without `lyrics` → auto-fallback copies lyrics from the source task. Full resolution chain (`SunoTaskHandler#resolve_cover_prompt`), instrumental override, legacy `prompt` back-compat: `docs/architecture.md#cover-audio-mode-resolution`.
- **Combined "song + cover art" requests** — `compose_song` / `add_vocals` / `cover_audio` accept `with_cover_art: true`; the deduplicated chained `suno_cover_art` task is created only after the song is Telegram-accepted, locally persisted, and marked done. The original `forum_thread_id` must be copied to the child. The user already paid the bounded parent request, so the internal chain is not charged a second `suno` rate-limit slot. Detail: `docs/architecture.md#combined-song--cover-art-requests`.
- Suno cover-art uses a separate handler (`SunoCoverArtHandler`, output is images) and a different endpoint pair from compose/upload-cover. Its `ToolResult.action` provenance is image-only (`cover_art` / `suno_cover_art`): it must never authorize a song/audio completion or delivery claim. Failures emit `cover_art_failed` agent_event. Detail: `docs/architecture.md#cover-art-source-resolution`.
- Suno WAV export — `convert_to_wav` tool, `suno_wav_convert` task, `SunoWavConvertHandler`. Endpoint pair, `successFlag` enum, `taskId`+`audioId` requirement, clip_index → audioId mapping: `docs/architecture.md#suno-wav-export`.
- **`cover_art` source resolution** — chain: explicit `suno_task_id` → reply target's `bg_task_external_id` → most recent `done` Suno task. Full detail: `docs/architecture.md#cover-art-source-resolution`.
- **Suno error-detail propagation** — Suno's `errorCode`/`errorMessage` (e.g. `[413] "Uploaded audio matches existing work of art"`, `SENSITIVE_WORD_ERROR`) reach the agent as formatted, sanitized detail rather than a bare `:failed`. `SunoClient#poll_once`, `poll_wav_once`, and `poll_cover_art_once` return `{ failed: true, error: '<formatted detail>' }`; handlers thread it through `mark_failed_and_notify(... error_detail:)` so the agent can distinguish copyright reject, content flag, worker failure, and delivery/persistence failure. WAV polling explicitly distinguishes `{ wav_url: ... }`, `{ failed: true, ... }`, and unknown shapes. `SunoClient#format_suno_error` and every handler's `safe_suno_detail` strip URLs/secrets before logs, task state, notices, and events; terminal delivery results recursively redact CDN URLs. This is security-critical because some Suno 4xx bodies echo Telegram file URLs containing the bot token.
- **Shared durable Suno delivery (`SunoDelivery`).** Main songs, cover art, WAV, and separation first cache the paid provider result, reset the provider-poll attempt budget, and return `:pending`. A later cycle downloads and sends; no handler sleeps or loops on network failure. Telegram acceptance requires exactly the expected item count and an actual Ruby `Integer > 0` `message_id` for every item. Acceptance immediately checkpoints compact receipts (topic plus compact photo sizes for cover art), removes URL fields/substrings from the cached result without truncating lyrics, and moves to `persisting_delivery`; later cycles reconcile `Message.persist_bot_reply` by `(chat_id, message_id)` without resending. Main-song lyrics are their own durable post-audio stage: send once, checkpoint, then persist as a reply before final completion. Delivery and persistence each have a three-cycle cap through `mark_retrying!`. Terminal pre-acceptance failure is failed/failed. Exhausted persistence is failed/delivered with a `*_persistence_failed` event that forbids resend. Only full reconciliation becomes done/completed/delivered. Provider/Telegram error text and terminal cached URLs are sanitized. All sends, reconciliation writes, and direct notices use the snapshotted `forum_thread_id` as an explicit fallback.
- **Vocal/stem separation (`separate_vocals`)** — cuts tracks out of the ORIGINAL recording; `cover_audio instrumental=true` regenerates music instead, so "убери вокал / минус / караоке" must route to `separate_vocals` (both tool descriptions say so — keep them in sync). Modes `vocals`/`stems`/`instrument` → Suno `separate_vocal` (10 credits) / `split_stem` (50) / `split_stem_advanced` + `stemName` (20). Source is `taskId`+`audioId` OR `audioUrl` (≤20 MB), never both. **Never resubmit** after Suno accepted a job (every call is billed; empty SUCCESS → failure with detail, not `:retry`). Implied sources (no reply/attachment/url) are bounded to ≤30 min — the newest of a lookback upload and the latest same-topic bot song row — and are used **only on real user turns** (`tool_ctx[:user_initiated]`): cron/agent_event turns carry no audio/reply context, so "latest song" there could bill a track the user never pointed at. A message's own attachment beats the bot song it replies to. The source is resolved BEFORE the rate-limit check so a rate-limited deferral's intent names a concrete re-selecting call (`source_message_id=…` / `suno_task_id=…, clip_index=…`). Separation sends at most one ≤10-item group per TaskRunner cycle. It persists every accepted batch before advancing and checkpoints the next batch index, so already accepted groups are never resent after a crash or later failure. A batch is all-or-nothing: every source must download and every acknowledgement must validate. Final success is done/completed/delivered; exhausted later-batch delivery is failed/failed with truthful delivered/missing stem lists, while exhausted receipt persistence is failed/delivered and must not resend. `split_stem_advanced`'s response shape is undocumented — the parser falls back to `response.originData[]`; verify against a live response before trusting it. Detail: `docs/architecture.md#suno-vocalstem-separation`.
- **Submit error messages are load-bearing** (`SunoClient#post_for_task_id` → `submit_error`): raised on non-200 AND on HTTP 200 without `data.taskId` (Suno's body `code`/`msg` goes into the message — prod add-vocals "No taskId" failures 1044/1246/3789 lost it). URLs are always redacted: Suno echoes `uploadUrl`/`audioUrl`, i.e. the bot-token Telegram URL, and the message reaches the agent_event summary (DB + LLM) and TaskRunner's `Ошибка:` chat notice. Permanent codes (400/401/404/413/429) and 5xx are rendered bare so `TaskRunner#process_one`'s `\s4\d{2}[\s{]` / `\s5\d{2}[\s{]` regexes classify them; 405/430/455 are rendered `code=NNN` so they are NOT marked permanent. Changing the format changes retry behavior — `test_submit_error_code_rendering_matches_task_runner_classification` pins it against `TaskRunner::PERMANENT_ERROR_RE`/`TRANSIENT_ERROR_RE`. Every Suno handler's submit rescue checks `TaskRunner.permanent_error?(e)` first and fails with its own notice + agent_event (`*_rejected`); only retryable errors are re-raised — re-raising a permanent one makes TaskRunner post a raw `Ошибка: …` with no agent_event.
- **Upload-source generation failures never resubmit** — `poll_once` returns `{ generation_failed: true, error: }` for `CREATE_TASK_FAILED` / `GENERATE_AUDIO_FAILED` (with Suno's sanitized reason); `SunoTaskHandler#handle_generation_failure` schedules a later-cycle resubmit only for `suno_generate`, while `suno_cover_audio` / `suno_add_vocals` fail as `suno_source_rejected`. Prod 2026-07-20..09-13: 22 of 38 upload tasks failed and repeated submissions of the same file failed in a row (12 submits of one file across 3 tasks), yet the same recording went through weeks later—blind resubmits just ended in the agent silently composing a new song instead of the cover. Don't re-add an automatic resubmit for uploads; a retry must be deliberate and later (`retry_of_task_id`). `:retry` means only SUCCESS-without-clips and schedules a later-cycle resubmit. Every handler resubmit must call `mark_retrying!`, which increments canonical `retry_count` and sets phase `retrying`; reset `attempts` to 0 where the fresh external job needs a fresh poll budget (task 3715 timed out mid-resubmit). TaskRunner's next claim returns the phase to processing—do not encode this lifecycle only in params counters.
- **Upload failures are reported as what they are** — chat notice "Не удалось сделать кавер" / "Не удалось добавить вокал", agent_event `cover_failed` / `add_vocals_failed` with `task #ID` in the summary. The "don't swap in a from-scratch song without consent; offer retry_of_task_id / another file / lyrics" directive lives in `AgentEventHandler::EVENT_DESCRIPTIONS` (the summary is cut at 600 chars). Reporting a failed cover as `song_failed` ("Я попытался сгенерировать песню") is what nudged the agent into compose_song on 2026-08-24.
- **`retry_of_task_id`** on `cover_audio` / `add_vocals` — `BackgroundTask.id` of a **failed** task of the same type in the same chat (anything else → refusal string), refused when a `pending`/`done` task already carries the same `retry_of_task_id` (the source stays `failed` forever, so "повтори" + a cron intention would bill twice); copies source + params the call leaves empty. The new request's current `forum_thread_id` takes precedence; when absent (notably deferred/cron replay), fall back to the failed source task's topic. New upload tasks store `upload_file_id` and `SunoTaskHandler#fresh_upload_url` re-resolves the Telegram link at submit (getFile links expire ~1 h; retries run later, from cron, with no `ctx[:audio]`).
- **All Suno producer tools return task-bound action evidence.** `compose_song`, `add_vocals`, `cover_audio`, `cover_art`, `convert_to_wav`, and `separate_vocals` return `ToolResult.action` with their own action, positive DB task ID, concrete `suno_*` task type, queued phase, and pending delivery. Do not regress to prose-only acknowledgements: Runner needs that identity for later status/delivery claims and appends it to safe acknowledgements. `cover_art` is the sole image-family Suno action; the other five are audio-family evidence.
- **DM audio follow-up (`PendingAudioRequest`)** — when a source tool finds no audio on a real user turn in a private chat (and the bucket isn't exhausted), it registers the request and returns a plain string (NOT `ToolResult.deferred` — that would leave a scratchpad intention to redo later); the user's next captionless audio / audio document in that DM replays the request via `MessageResponder#run_pending_audio_followup`. DM-only, never voice notes, never edits, cleared by any newer GptChat turn from that user AND by `PendingAudioRequest.clear_for(ctx)` right before any Suno tool creates a task (a turn may offer, then find a source in a later iteration), 10-min TTL, in-memory. It is the one deliberate exception to "captionless audio doesn't trigger the bot" — keep it that narrow.
- **Model selection** — one optional `model` param (`SUNO_MODEL_PARAM` in `_suno_language_rule.rb`, enum from settings via `enum_source` — Settings isn't loaded at tool-require time) on `compose_song` / `cover_audio` / `add_vocals`, stored in `task.params['model']` so resubmits and `retry_of_task_id` retries keep it. Validate the agent's model **in the tool** with `SunoToolModel.resolve` (before the rate-limit check): an unknown explicit model returns an error listing `SunoClient.allowed_models` — submit-time fallback alone meant "на v5" was answered "queued" and silently ran on the default. Inherited models (retry source) that are no longer allowed → default, no error. Rate-limited deferred intents append `SunoToolModel.intent_suffix(model)` so the cron retry keeps the model. `SunoClient#resolve_model` stays the last line of defence at submit (case-insensitive match; anything else → default with a WARN — never let an unvalidated model reach Suno, it would 400). Never reintroduce the `'V4'` fallback (tighter limits: lyrics 3000 / style 200 / title 80). Keep the model optional in the schema — required params force the LLM to pick one every call. `model_name` from `poll_once` (Suno's `modelName`) is logged on completion — grep `model_name=` to verify what actually ran. Prod `settings.yml` has no `suno.model` override (checked 2026-09-13); if one is added, it wins over the committed default.
- **add-vocals `negativeTags` is always sent** (empty string when none) — required by that endpoint; the other submits still drop it when empty.
- Suno API settings in `config/settings.yml` under `suno` group: `api_key`; non-secret config (`api_url`, `model`) in `settings.common.yml`
