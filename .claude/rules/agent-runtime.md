# Agent runtime gotchas

Trap knowledge for the agent loop, tools, scratchpad, event loop, and cron. Reference: `docs/architecture.md` § Agent Mode / § Agent Scratchpad / § Agent Event Loop.

| Task | File |
|------|------|
| Agent mode tools | `lib/agent/tools/*.rb` + `lib/agent/tool_registry.rb` + `lib/agent/runner.rb` |
| Agent scratchpad | `lib/agent/scratchpad.rb` + `models/chat_state.rb` + `lib/agent/tools/scratchpad.rb` (`remember`/`forget` tools); auto-rendered as `{SCRATCHPAD}` in agent_prompt template |
| Agent event/error bridge | `lib/agent/error_reporter.rb` + `lib/task_handlers/agent_event_handler.rb` + `lib/task_handlers/agent_event_emitter.rb`. Tool exceptions return in-loop; async failures re-enter through `agent_event`. |
| Time-deferred intentions | `lib/cron_scheduler.rb` (60s tick) + `Agent::Scratchpad.due_intentions` / `mark_acted`. Started from `lib/bot.rb`. |
| Agent views historical images | `lib/agent/tools/view_image.rb` (tool) + `lib/telegram_file.rb#download_image` (shared download) + `Agent::Runner#inject_pending_images` (vision injection + `agent_vision` upgrade) + `lib/message_responder.rb#photo_attachment_file_id` (persistence) |
| Agent inspects bot state | `lib/agent/tools/bot_state.rb` (`inspect_bot_state`, admin-only) + `lib/agent/tools/task_status.rb` (member-safe, current-chat only) + `TaskRunner.state_snapshot` |

- **NEVER `sleep` (or otherwise block) in a tool handler.** Handlers run synchronously inside `bot.listen`'s single-threaded loop — a sleep freezes the whole bot for every chat — and, on the TaskRunner path, inside `with_connection` with only 2 workers. This killed the "wait for the dice animation" idea in `challenge_rule`: `api.send_dice`'s response carries the rolled value immediately (the client animation runs ~4s), so the verdict returns at once instead of sleeping through the animation.
- Agent mode is the only mode: `GptChat` / `GptQuestion` always route through `Agent::Runner`, which lets GPT call bot tools (radio, weather, search, etc.) autonomously. Agent supports vision — replying to a photo with "бот ..." sends the image to the vision model for recognition.
- **Turn telemetry** — every `Runner#run` emits one structured `METRIC` JSON line in `bot.log`, including total `took_ms`, loop `iterations`, `llm_calls`, executed `tool_calls`, integrity `corrections`, final `status`, and final setting. The `ensure` wrapper emits it for early returns and exceptions; telemetry failures never replace the user result. Keep per-provider-call `took_ms` in `gpt.log` as the lower-level latency source.
- All `бот <text>` requests — including search, images, gifs, horoscope — route through `GptChat` → `Agent::Runner`. The agent's `google_search` / `horoscope` / `generate_image` tools handle those intents and can compose multiple tools in one turn (e.g. "бот найди новости и нарисуй" → `google_search` then `generate_image`). There are no direct-dispatch commands for search or horoscope anymore.
- **`inspect_bot_state` is read-only and admin-only.** It may expose global queue counts, runner health, processing task IDs, and non-secret model names, but task details are always scoped to `ctx[:chat_id]`; a supplied task ID from another chat is treated as absent. Never add raw params/results, API keys, external IDs, URLs, or other-chat content to this tool. `TaskRunner.state_snapshot` returns mutex-protected copies rather than live mutable collections.
- **`task_status` is the member-safe source of task truth.** It always filters by `ctx[:chat_id]`; another chat's ID looks absent. Explicit ID/limit validation stays strict. Without an ID it returns at most five newest user-facing image/Suno tasks (creation time then ID), excluding agent events, knowledge/cron, and housekeeping rows. One result is single-task evidence. Multiple results use compact validated `items` with action/task_id/task_type/status/phase/delivery and terse ID-only user text, staying under Runner's 2KB result cap; the outer batch is deliberately deferred/unknown unless all items are completed/delivered. It reads only migration-026 lifecycle columns—never params/results/`params_hash`, external IDs, prompts, URLs, secrets, or inline base64. `processing_cycles` is handler/poll work; `retry_count` is explicit bounded transitions. Missing/invalid/unavailable lookup is deferred/unknown, never guessed state.
- Agent scratchpad (`Agent::Scratchpad`, `chat_states` table) — per-chat working memory (intentions/notes/expectations), distinct from knowledge base. Hard cap 6000 chars with FIFO eviction. Rendered as `{SCRATCHPAD}` in `agent_prompt`; managed via `remember`/`forget` tools. Detail: `docs/architecture.md#agent-scratchpad`, ADR-003. **Rules-war `rules` category invariants constrain scratchpad edits — see `.claude/rules/agent-games.md`.**
- Agent event loop — `agent_event` task type, `AgentEventHandler`, `AgentEventEmitter` mixin, and centralized `Agent::ErrorReporter`. Tool handler exceptions become structured JSON tool results in the current Runner iteration. Terminal background-task failures plus respond/delivery, dispatcher, poller, and provider failures enqueue sanitized `runtime_error` events. Task events dedupe on `parent_task_id`, so tailored image/Suno events win over the generic fallback; parentless failures coalesce by sanitized fingerprint for 5 minutes and retain the 10/hour/chat cap. Image failure events are user-facing agent turns: they must answer in the originating forum thread, and `AgentEventHandler` supplies a task-ID-bearing deterministic fallback if the Runner raises or returns blank/`(skip)`. Agent-event replies are cached before send, require a strict positive-integer Telegram acknowledgement, and persist that acknowledgement before completion; persistence retries reuse the receipt without rerunning the agent or resending. If the event cap or insert prevents an image event, a dedicated `failure_notice` task owns the same strict, bounded, receipt-first delivery and suppresses the generic parent error event. It catches transport/Telegram exceptions inside the handler so every cycle spends the five-attempt budget; on exhaustion it marks itself failed with delivery `delivered` iff a receipt exists, and returns `:failed` without TaskRunner's generic timeout notice/runtime event. **Synthetic users are role `member`, never `admin`; `runtime_error` Runner turns set `tools_enabled: false`, reject provider-supplied tool calls at execution time, and HTML-escape details inside the untrusted delimiter.** A failed `agent_event` never emits another event. Detail: `docs/architecture.md#agent-event-loop`, ADR-003 PR-2.
- **Image watchdog (`Runner#run`)** — the model sometimes promises/describes an image but never calls `generate_image`, so nothing is delivered (silent). Two triggers detect it: (1) `hallucinated_image_caption?` — output text imitates the `🎨 <caption>` format (keys off model OUTPUT); (2) `image_request_unanswered?` — the user's request matches `DRAW_DIRECTIVE` (imperative нарисуй/дорисуй/… stems, Cyrillic-stem match since Ruby `\b` is ASCII-only) or, when a source photo is present, `IMAGE_EDIT_DIRECTIVE`. An explicit attached/replied-photo edit bypasses a no-tool/refusal response and calls `generate_image` directly with the raw request, `edit_source: true`, and a deterministically recognized model mention (Wan/Qwen/Seedream/Sunburst/Nano Banana/Flux); this prevents the vision chat model from becoming a policy gate. If that direct tool call fails, its structured error is appended as a nudge and the Runner iterates again instead of returning JSON to Telegram. Other triggers still nudge the model once. **Request triggers are gated to `@user_initiated` real user turns** (gpt_chat/gpt_question): the `agent_event` path passes `user_initiated: false` because its synthetic prompt echoes the original `Запрос: …` into `@text` and would otherwise re-trigger image-gen on the event loop. `DRAW_DIRECTIVE` deliberately excludes `сгенерируй` (generic "generate" — пароль/текст/идею aren't images).
- **Blank agent replies (`Runner#run`)** — no tool calls + nil/whitespace text. On agent_event/cron turns (`user_initiated: false`) the Runner returns `""`, which `AgentEventHandler` counts as silence — never turn it into a forced reply there. On user turns: `stop` `length`/`max_tokens` → stub immediately (a retry repeats the runaway and blocks the loop); otherwise one retry **with tools** — never route a blank user turn into the tool-free MAX_ITERATIONS finalizer (it can't call `generate_image`/search and invites made-up answers), and keep the draw-directive watchdog reachable (a blank reply to «нарисуй» gets the image nudge). Don't replay the blank assistant turn: on DeepSeek it carries the whole `reasoning_content`.
- **Task-status watchdog (`Runner#run`)** — when a real current-user request explicitly asks for the status/progress/lifecycle of a background task and the model tries to finish without ever calling `task_status`, Runner performs that read-only call once, using the one unambiguous parsed task ID or no ID for recent tasks. It injects a provider-valid synthetic tool-use/result pair and lets the model finish through the normal trusted-evidence integrity gate. Detection reads only `@text`, strips quoted/code blocks, rejects examples/history/translation/meta requests, requires both a task subject and lifecycle question, refuses multiple IDs, never runs on synthetic/tools-disabled turns, and never duplicates a model-issued `task_status` call.
- **Agent tool ctx — `ctx[:api]`** — Tools read `ctx[:api]` for Telegram calls. Pass `api:` to `Agent::Runner.new`; Runner warns if nil. Detail: `docs/architecture.md#agent-event-loop`.
- **Tool ctx provenance keys** — `ctx[:audio_source]` (`:message`/`:reply`/`:lookback`, from `AudioAttachment`), `ctx[:user_initiated]` (false on agent_event/cron turns) and `ctx[:forum_thread_id]` (set only in forum chats). Tools that pick an IMPLIED target (no reply/attachment/explicit id) must require `user_initiated` — synthetic turns have no audio/reply context, so "latest X" there is a guess that can bill the wrong thing — and should put a concrete re-selecting argument (message_id / task id) into any deferred intent. `separate_vocals` is the reference implementation. Also in ctx for `PendingAudioRequest`: `ctx[:private_chat]`, `ctx[:request_text]` (the Runner's `@text`), `ctx[:message_id]`.
- **Suno upload failure events** — `cover_failed` / `add_vocals_failed` (from `SunoTaskHandler`) and `separation_failed` / `separation_delivery_failed` have their own `EVENT_DESCRIPTIONS`. Put behavioral directives for the agent there, not in the summary (`build_event_prompt` cuts the summary at 600 chars).
- **`Agent::ToolResult` action contract and provenance** — `.action` validates bounded action/task-type names, positive task IDs, non-negative sent counts, phase/delivery allowlists, and optional multi-task `items`. Runner keys evidence by `(action, task_id, task_type)`; newest evidence supersedes stale evidence and invalidates exact old-payload unwrapping. Provider-authored JSON is never trusted. Specific phase/delivery overrides coarse status. `generate_image`, `make_award` (also keyed as `generate_image`/`image_generate`), and every Suno producer (`compose_song`, `add_vocals`, `cover_audio`, `cover_art`, `convert_to_wav`, `separate_vocals`) return their created task ID/type plus queued phase/delivery; task-status batches preserve every task's ID/type/action. Deferred results share the provenance path but cannot authorize task state without an identity.
- **Operational claims bind to identities.** Explicit `задача #N`/`task #N` selects that ID and must match image/audio type. `cover_art`/`suno_cover_art` is image-only provenance; it cannot authorize an audio/song claim. Unnumbered claims require exactly one matching item in the latest batch; several are ambiguous. Mixed-task sentences are checked independently. Elliptical follow-ups («готово», «всё есть», «смотри выше») count as completion/delivery when the user asked for status/result. Outside those contextual ellipses, require a task noun grammatically tied to its lifecycle predicate; descriptive vision prose containing the same vocabulary in unrelated clauses must not trip the task-claim gate. Safe acknowledgements append trusted task ID(s) if omitted. Queued evidence cannot authorize running, completed+unknown cannot authorize delivered, and audio evidence cannot authorize an image claim.
- **Final-output integrity is a runtime boundary, not just a prompt request.** It rejects internal/provider markers, sentinels/deferred prefixes, registered-tool syntax, inline/fenced/nested/array tool payloads, and unsupported operational claims. A real turn gets one correction at most; no correction-pass tool call executes, and corrected text crosses the same boundary. Synthetic turns suppress invalid text. Fallback is generic for leakage and explicit unknown-status for unsupported task state. Genuine JSON/code is allowed only when it contains neither internal/provider syntax nor tool payloads nor operational claims lacking evidence; technical framing is never a bypass.
- `CronScheduler` (`lib/cron_scheduler.rb`) — 60s tick, fires `agent_event(cron_tick)` for chats with due scratchpad intentions; same 10/hr rate cap as agent_event. Started from `lib/bot.rb`. Detail: `docs/architecture.md#agent-scratchpad`.
- Scratchpad compaction is pure-Ruby (no LLM); runs inline on every `Scratchpad.add` for expiry-based pruning. Manual: `rake scratchpad:compact [MAX_AGE_DAYS=N] [CHAT_ID=...]`. Detail: `docs/architecture.md#agent-scratchpad`.
- **`view_image` mid-loop vision upgrade** — the tool fetches a stored photo (by `message_id` of a `photo: true` context row) and returns `Agent::ToolResult.image`; Runner queues it in `@pending_images`, injects it AFTER all of the iteration's tool-result messages (openai contract: every tool_call answered before another role), then flips `@setting` to `agent_vision` for the rest of the turn. The upgrade only happens when `agent` and `agent_vision` share `api_type` (`ctx[:can_view_image]`, computed at Runner init) — accumulated messages are provider-shaped and can't be replayed cross-provider; on mismatch the tool degrades to text. DeepSeek's `reasoning_content` is stripped from accumulated assistant messages on upgrade (grok may reject the unknown field). `materialize_result` checks `image?` BEFORE the deferred guard — reordering would silently drop the image. `GptMaster#dump_gpt` redacts base64 image payloads from gpt.log. Photos persist at ≤1280px (`Message.pick_photo_file_id` — shared by incoming `save_message` and outgoing `persist_bot_reply`); the bot's own sent images (deliver `:image`, image_gen, Suno cover art) are captured too, so the agent can re-view its generation results. Only post-deploy photos are fetchable; document-images (`image/*` MIME files) aren't captured.
  - **Same resolution reused for edit sourcing:** `generate_image`'s `source_message_ids` lets the agent pick history photos as *edit inputs* (combine), resolved the same way (`message_id` → `attachment_photo_file_id` → `TelegramFile.download_image`) — but the download happens in `ImageGenTaskHandler` (TaskRunner), NOT the tool, because the tool runs in the bot's listen loop (no blocking I/O). See `.claude/rules/image-gen.md`.
