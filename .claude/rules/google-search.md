# Google search gotchas

Reference: `docs/architecture.md` § Gogolmogol.

- Google API keys are a pool in settings — `gogolmogol.rb` cycles through them
- **`google_search` intent is explicit:** the agent passes `media_type: 'text'|'photo'|'gif'` on every call (JSON-Schema enum, all tool params are auto-required). No query-string regex sniffing; `Gogolmogol.new(query, media_type:)` uses the intent directly to set `searchType=image` + `fileType=gif`. `download_results` includes an SSRF guard — http(s) only, no loopback/private/link-local literal IPs (DNS-based + redirect-target rebinding are residual risks). Tool file holds Telegram coupling (`sendMediaGroup` / `sendAnimation`); Gogolmogol stays Telegram-unaware.
- **Media results separate Telegram acceptance from local tracking.** `photo`/`gif` return `[media_delivery status=sent|partial|failed|sent_untracked kind=... sent_count=N accepted_count=N persisted_count=P rejected_count=R ambiguous_count=A requested_count=M]`; `sent_count` is a compatibility alias for Telegram-confirmed `accepted_count`, not the DB count. Acceptance requires `message_id` to be an actual Ruby `Integer > 0`; numeric strings, zero/negative values, and truthy typed/hash/nested responses without one are malformed and unconfirmed. Because `sendMediaGroup` is atomic, a photo-group acknowledgement is authoritative only when it contains exactly the requested number of **distinct** valid message ids. A short, sparse, malformed, or duplicate acknowledgement is `sent_untracked` with every requested item counted ambiguous: persist no subset, expose no fallback URLs, and tell the agent not to retry because Telegram may have accepted the whole group. Timeout, EOF, connection reset, and unknown transport/HTTP exceptions are equally ambiguous because they may occur after acceptance; sanitize their details, expose no source URLs, and forbid automatic resend. Only an explicit Telegram rejection (for example `IMAGE_PROCESS_FAILED`, `Bad Request`, or another definite non-transient 4xx) is rejected and may expose its retry URL. Individually sent GIFs use the same classification per item: mixed batches keep accepted/persisted, definitely rejected, and ambiguous counts separate; any ambiguity makes the overall status `sent_untracked`, while `partial` is reserved for confirmed accepts plus definite rejects. `sent_untracked` also covers confirmed acceptance followed by incomplete local persistence after an existing-row check plus one bounded DB retry. Never resend accepted or ambiguously acknowledged media merely because local persistence failed.
- **Validated media-group mapping is positional.** Only after the whole group acknowledgement passes exact-count/distinct-ID validation may each response element be paired with the downloaded source at the same array index. Never compact malformed entries or persist a partial mapping. GIFs apply accepted/persisted accounting individually and may expose fallback links only for definite per-item rejection. Both media paths pass `ctx[:forum_thread_id]` as `message_thread_id`; `IMAGE_PROCESS_FAILED` means Telegram rejected that media.
- **Persist in the originating topic even when Telegram omits it.** Pass `ctx[:forum_thread_id]` both to `sendMediaGroup`/`sendAnimation` and explicitly to `Message.persist_bot_reply`; the response thread id is not a reliable sole source for local context. Sanitize every exception string with `Agent::ErrorReporter.sanitize` before logging or returning it to the agent.
